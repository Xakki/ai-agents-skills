# Deadlines, cancellation and asynchronous failures

Start the appropriate monotonic total deadline at the owning boundary, propagate remaining budget to every await and bound any permitted cleanup. Distinguish request-kind, idle/no-progress, transport and human-input deadlines; a lower-layer cap can defeat a raised caller value. Preserve unrelated approval or authentication windows. A per-attempt fallback window may reset only within the original total. Test exact deadline transitions and decreasing budgets with fake clocks or controlled barriers, not long sleeps or real credentials.

If the contract requires trying later fallback candidates, reserve an appropriate bounded budget for each attempt rather than letting the first consume all remaining time. Where a synchronous release path owns asynchronous handlers, verify it bridges cancellation and lifecycle cleanup to the correct event loop; removing a socket or marker alone does not prove the handler settled.

Keep timeout, connection failure, identity mismatch, invalid response, unavailable owner and caller cancellation distinct; avoid exposing dynamic secret-bearing error data. Cleanup errors during an active semantic timeout must not accidentally change its terminal classification or trigger retries; outside that case preserve normal cleanup error behavior. Stop new admissions before cancelling and joining active handlers, then close resources owned by the exact generation. An old callback must not remove or invalidate a replacement task's state.

Cooperative cancellation alone cannot guarantee a hard wall-clock limit if a dependency or cleanup suppresses cancellation. When the approved contract requires and permits a hard deadline, use a supported separately supervised isolation boundary and test a cancellation-resistant child; otherwise state the softer guarantee. Process termination still requires explicit authority and verified ownership.

For a synchronous worker handing results to an async loop, keep worker exceptions and main-task cancellation separate. Marshal completion through the loop's supported thread-safe mechanism; check completion/cancellation on the receiving loop immediately before settling, so late workers cannot overwrite a timeout or raise unhandled errors. Do not leak original provider exception text or control-flow exceptions when the boundary requires sanitized errors. Test late success/failure, cancellation and loop shutdown through the actual handoff.

When a consumer inspects and then forwards a one-shot iterable, preserve the actual single-pass contract: materialize once only where supported and bounded, keep ordering, and do not duplicate payload bytes or alter `None`/reusable-collection semantics. Test the real entrypoint and selected consumer rather than only a classifier.
