# yandex-oauth-token — reference

Full flows, curl examples, service-wiring pattern and diagnostics for Yandex OAuth (Yandex ID)
user-scoped tokens. Placeholders only — never substitute real values here.

## Concepts

- **Yandex OAuth / Yandex ID** issues **user-scoped** tokens (they belong to a specific Yandex
  account, not to the app).
- **Auth header** for the Metrika API: `Authorization: OAuth <token>` — note **`OAuth`**, not
  `Bearer`. Using `Bearer` fails.
- **Endpoints**:
  - authorize: `https://oauth.yandex.ru/authorize`
  - token: `https://oauth.yandex.ru/token`
  - Metrika management (probe): `https://api-metrika.yandex.net/management/v1/...`
- **Scopes**:
  - Metrika **Logs API** (create/download logrequests) → `metrika:read` is **sufficient**.
  - `metrika:write` → only for editing counters / uploading data.
  - Independent of scope, the token's **account** needs at least **guest read** access to the
    specific counter.
- **`client_credentials` grant does NOT work for user data.** You cannot mint a user token from
  `client_id` + `client_secret` alone; a one-time browser consent by the resource-owning account is
  always required.

## Getting a token — two flows

### A. Implicit flow (fastest, NO refresh_token)

Use only for quick manual/one-off tokens — there is no refresh, so it must be regenerated by hand
when it expires.

1. Register/select an app at `https://oauth.yandex.ru/client/new` with the needed permission
   (e.g. `metrika:read`); copy the **ClientID**.
2. Open in a browser **logged in as an account WITH access to the resource**:
   ```
   https://oauth.yandex.ru/authorize?response_type=token&client_id=<CLIENT_ID>
   ```
3. Approve → the `access_token` is shown (also in the URL fragment `#access_token=`).
   **No `refresh_token`** is issued.

### B. Authorization-code flow (recommended for services/cron — yields a refresh_token)

1. One-time, in a browser **logged in as the right account**:
   ```
   https://oauth.yandex.ru/authorize?response_type=code&client_id=<CLIENT_ID>
   ```
   → a short-lived, **single-use** `code` (~10 min TTL; shown on-page or in the redirect `?code=`).
2. Exchange the code server-side (needs `client_secret`):
   ```
   curl -sS -X POST 'https://oauth.yandex.ru/token' \
     --data-urlencode 'grant_type=authorization_code' \
     --data-urlencode 'code=<CODE>' \
     --data-urlencode 'client_id=<CLIENT_ID>' \
     --data-urlencode 'client_secret=<CLIENT_SECRET>'
   ```
   Response JSON:
   ```json
   { "access_token": "...", "refresh_token": "...", "expires_in": 31536000, "token_type": "bearer" }
   ```
   (`token_type` in the JSON is informational — you still send `Authorization: OAuth <token>` to
   Metrika.)

## Refreshing (non-interactive)

```
curl -sS -X POST 'https://oauth.yandex.ru/token' \
  --data-urlencode 'grant_type=refresh_token' \
  --data-urlencode 'refresh_token=<REFRESH_TOKEN>' \
  --data-urlencode 'client_id=<CLIENT_ID>' \
  --data-urlencode 'client_secret=<CLIENT_SECRET>'
```

- **Refresh_token rotation.** Yandex MAY return a **new** `refresh_token` in the response. Persist it
  (overwrite the stored one) atomically — otherwise the next refresh uses a stale token and fails.
- **Always `--data-urlencode`.** Yandex tokens can contain `+ / =`; a bare `-d` corrupts them via raw
  form-encoding. This applies to `refresh_token`, `code`, and `client_secret` alike.

## Diagnostics

| Symptom | Most likely cause | Fix |
|---|---|---|
| `403 access_denied` ("Access is denied") on a Metrika call | Token account **lost access** to the counter, token **revoked** (app deleted / password changed), or **expired**. NOT a scope typo — scope is fixed at issue-time. | Regenerate/refresh from an account that **currently** has counter access. Beware the account-identity trap below. |
| `401` | Missing/invalid token or wrong scope. | Re-check header (`OAuth`, not `Bearer`), token validity, and requested scope. |
| Token silently stops working after months | Finite `expires_in` reached, or long-lived token aged out. | Refresh (code flow) or regenerate (implicit flow). Yandex recommends refreshing long-lived tokens ~every 3 months. |

**Account-identity trap:** "I have access to the counter" refers to a **login**. The token belongs
to whatever account **originally authorized** it, which may be a different account than the one you're
looking at. When a token gets `403`, confirm *which* account minted it and whether *that* account
still has counter access.

**Token lifetime:** trust the `expires_in` returned at issuance. Implicit-flow tokens can only be
fixed by manual regeneration; code-flow + `refresh_token` enables non-interactive renewal.

**Quick validity probe (never prints the token):**
```
curl -sS -o /dev/null -w '%{http_code}' \
  -H "Authorization: OAuth $TOK" \
  https://api-metrika.yandex.net/management/v1/counter/<COUNTER_ID>
```
`200` = valid, `403` = access lost/revoked/expired.

## Wiring into a service (generic pattern)

- **Store** `token` + `refresh_token` + `client_id` + `client_secret` in an env/secret file
  (e.g. `.env.local`), **never hardcoded** in source.
- **Refresh script (cron):**
  1. Read creds from the env file by parsing `^KEY=` lines — **do not `source`** the whole file
     (avoids executing arbitrary content and mangling values with special chars).
  2. POST the `refresh_token` grant (see above).
  3. On success, **atomically rewrite** the env file: build it with `awk` passing values via
     `ENVIRON[...]` (so `+ / =` in tokens survive), write to a temp file, `chmod --reference` the
     original, then `mv` over it.
  4. **Persist a rotated `refresh_token`** if the response contained a new one.
  5. **Reload/recreate** the consumer so it re-reads env.
- **Never log/echo token values.** On failure, alert with only `error` / `error_description`.
- **Env injection caveat:** if the consumer reads the token from **process env injected at container
  start**, an env-file change requires a container **RECREATE**, not a hot reload.

## Helper script (scripts/yandex-oauth.sh)

Bundled implementation of the wiring pattern above. Requires **`jq`** + **`curl`**. Reads secrets from
`ENV_FILE` and **never prints them** — output is limited to lengths / `expires_in` / HTTP codes.

**Config (env vars):**

- `ENV_FILE` (default `.env.local`) — the `KEY=VALUE` file it reads creds from and writes tokens back to.
- `OAUTH_PREFIX` (default `OAUTH`) — key prefix. The script derives four key names:
  `<PREFIX>_CLIENT_ID`, `<PREFIX>_CLIENT_SECRET`, `<PREFIX>_TOKEN`, `<PREFIX>_REFRESH_TOKEN`.

**Subcommands:**

- `authorize-url` — prints the browser URL (`response_type=code`) to obtain an auth `code`.
- `exchange <CODE>` — exchanges a code → `access_token` + `refresh_token`, saving both into `ENV_FILE`.
- `refresh` — uses the stored `refresh_token` → new `access_token`; **persists a rotated refresh_token**
  if the response carried a new one (writes only `<PREFIX>_TOKEN` otherwise).
- `check [COUNTER_ID]` — probes validity: with a counter id hits Metrika management, else
  `https://login.yandex.ru/info`. Prints `HTTP=<code>` (`200` valid, `401/403` invalid/lost-access).

It parses `^KEY=` lines (does **not** `source` the file) and rewrites atomically via `awk` +
`chmod --reference` + `mv`, passing values through `ENVIRON[...]` so `+ / =` in tokens survive.

**Example (a project's metrics token under prefix `OAUTH_METRIC`):**

```
OAUTH_PREFIX=OAUTH_METRIC ENV_FILE=.env.local scripts/yandex-oauth.sh authorize-url
OAUTH_PREFIX=OAUTH_METRIC ENV_FILE=.env.local scripts/yandex-oauth.sh exchange <CODE>
OAUTH_PREFIX=OAUTH_METRIC ENV_FILE=.env.local scripts/yandex-oauth.sh refresh
OAUTH_PREFIX=OAUTH_METRIC ENV_FILE=.env.local scripts/yandex-oauth.sh check <COUNTER_ID>
```

**Env-injection caveat:** if the consumer reads the token from process env injected at container
start, **recreate the container** after `exchange`/`refresh` changes the token — a hot reload won't
pick up the new value.

## Security

- Never commit real tokens/secrets. Keep secret env files **gitignored**, with **empty tracked
  placeholders** (e.g. `.env.local.dist`) so structure is versioned but values are not.
- Never print tokens to logs / chat / notifications. If you must reference one, **mask to length**
  (e.g. `len=41`), never the value.
