# Cross-repository handoff and evidence

Establish the authorized operations separately for each repository: card
administration, source inspection, implementation, tests and runtime changes
are distinct scopes. If access is limited to task administration, inspect only
permitted instructions and cards; use attributed, revision-pinned evidence
provided through an authorized route. A dependency does not grant access to the
other repository's source, Git state or runtime.

A scope restriction does not waive an acceptance criterion. Before splitting a
cross-repository deliverable, obtain the required decision and consistently
update the parent, child and successor prerequisites. Find an existing relevant
follow-up before proposing a new one. Record the delivered prerequisite, its
revision or artifact identity, outstanding consumer work and the next gate.
Report a verified producer contract separately from actual consumer integration;
a synthetic upstream or downstream fixture does not prove the real consumer ran.

After an authorized card transition, re-read the canonical destination and
verify that any embedded status agrees with its stage and that there is one
physical active card. Check the changed card and applicable parent; distinguish
new attributable validation failures from unchanged pre-existing board findings.
Preserve history while correcting stale statements that appear to describe the
current stage.

Tie each check to the revision and inputs actually exercised. Carry evidence
forward only when its covered inputs remain unchanged, and identify both the
original execution revision and the later revision. A metadata-only card change
is not a new execution of the earlier gate. Distinguish artifact identity from
runtime source revision when they differ, and report omitted checks as unrun.
