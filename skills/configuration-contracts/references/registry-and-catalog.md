# Registry and catalog consistency

When a configuration or published catalog selects registered capabilities,
identify the authoritative declaration, factory or lazy registry, configured
route, resolver, actual implementation and public projection separately. A
class or declaration alone does not prove registration, routing, account
entitlement, current upstream support or live health. Resolve canonical identity
and aliases at their documented scope; an upstream identifier may collide
across accounts or providers. Use authoritative product evidence and record
unknowns instead of inferring runtime behavior from a static file.

Define the meaning and dimensions of every reported count: unique items,
routes, nested targets and cross-provider edges may differ. Compare an
independently defined exact set and any promised order or aliases, not only a
count or permissive subset. For a scoped removal or correction, capture the
baseline and test the intended semantic delta plus unchanged siblings. Follow
the project's real policy for missing and empty restrictions; do not impose one
universal catalog or fallback rule.

If a listing promises static-only behavior, inspect its real assembly path and
test that listing does not invoke lazy discovery, provider initialization,
credentials or transport. Include an allowed positive control. Exercise the
actual route and source artifact separately from mock-driven selection, and
check downstream catalog and execution consumers. Report static, synthetic,
account-scoped and authorized live evidence separately.
