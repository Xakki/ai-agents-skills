# Stateful and generated-state cutovers

Inventory the actual source and destination, ownership, dependencies, data stores, durable offsets or leases, service identities and allowed effects. Decide the authorized snapshot, cutover sequence, acceptable interruption and recovery criteria before starting. Preserve the source and any existing destination state; use data-store-supported consistent snapshots rather than copying a live database or its partial files. Transfer secrets only when explicitly authorized and through a protected interface; report only permitted metadata.

Stage the new candidate and verify its available dependencies before switching ownership. If a consumer, lease or identity must be single-owner, establish the old owner has stopped before activating the new one. Bind a checkpoint or offset to its corresponding durable state. Test the exact accepted runtime path where authorized, and distinguish static checks, local smoke and live external readback.

For configuration generated from live resources, establish whether a valid empty initial state is supported, validate actual resource identities after creation, and snapshot the current accepted state before transitioning dependent services. Publish a validated candidate through the supported atomic mechanism and reconcile consumers to that candidate. On a failed transition, restore the intended prior configuration and all dependent components consistently under the authorized rollback plan; report any incomplete restoration. Do not assume a specific database, manifest schema, process manager, container system or filesystem semantics.

When a change affects a running process's startup environment or mounted resources, determine whether the supported reload or restart actually updates that boundary; some runtime changes require recreation or a newly launched process. Verify the effective running state, keeping the configuration edit, activation and dependent reload as separately authorized effects.
