# Interactive workflow communication

For status, state what has completed, what is running, what is verified and what remains; a request for status does not itself pause or restart work. Preserve the current goal, settled decisions, running process identity and explicit exclusions across follow-ups or context compaction. Distinguish an owner-reported action from independently verified behavior.

Ask a decision only when missing information or authority matters. Group independent questions, explain material choices and their effects, use available interaction controls, and continue independent authorized work while waiting. A timeout or silence is not approval. A choice grants only its stated scope and does not bypass a separate native security or approval boundary. Do not repeat an already granted decision.

When scope changes, map each response to its original item, retain exclusions and explain the next actual action without broadening the assignment. For an inventory, identify its source and scope, deduplicate genuine aliases, reconcile counts, report inaccessible or partial results, and do not equate a listed status with verified completion. Drafting an autonomous-goal prompt is not permission to start it. Use the actual runtime interface; do not assume agent-specific buttons, timers or notification behavior.

For research or design of interactive request, approval or reminder lifecycles, consult [decision lifecycle research](references/decision-lifecycle.md); this is design guidance, not evidence that the current runtime supports any particular control.
